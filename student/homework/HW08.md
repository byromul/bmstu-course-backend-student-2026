## Создайте точное дерево этапа

Создайте:

```text
game/authentication.py

```

Измените `game/models.py`, `game/api_views.py`, `game/management/commands/import_scenario.py` и `contracts/openapi.yaml`. Создайте `game/middleware.py` для безопасного журнала запросов. `game/migrations/0002_scenario_owner.py` создаёт генератор Django.

## Добавьте владельца модели

Свяжите `Scenario.owner` с пользователем Django. Выберите `on_delete`, соответствующий контракту курса, и объясните последствия удаления пользователя.

Существующие сценарии воспроизводимы из YAML, поэтому переход выполняется явно:

1. Остановите сервер;
2. сохраните диагностическое состояние;
3. удалите только воспроизводимые сущности сценария из локальной базы;
4. измените модель;
5. создайте миграцию;
6. примените миграцию;
7. повторно импортируйте сценарий с явным владельцем.

Пользователи и токены не удаляются как данные сценария.

Наблюдаемый результат — `0002_scenario_owner.py` применена, а последняя команда возвращает код `0`.

## Измените импорт явно

Команда принимает обязательный аргумент владельца:

```bash
python manage.py import_scenario data/scenario.yaml --owner anton
```

Она находит существующего пользователя, назначает его сценарию на сервере и сохраняет идемпотентность. Неизвестный пользователь приводит к контролируемому отказу до изменения сценария.

Клиент не передаёт поле `owner` как доверенное значение.

## Настройте непрозрачный Bearer

В `game/authentication.py` создайте производный класс DRF `TokenAuthentication`, изменив только ключевое слово на `Bearer`. Не создавайте собственный формат токена и не превращайте его в JWT.

Подключите `rest_framework.authtoken` и выполните его миграции. Пользователя и токен создайте через административную панель либо документированную локальную команду, которая не печатает токен в журнал и не записывает его в Git.

## Реализуйте объектное разрешение

В `game/permissions.py` создайте разрешение владельца. Оно допускает действие, только если `scene.scenario.owner == request.user` либо соответствующий сценарий операции принадлежит пользователю.

Все четыре операции требуют аутентификацию. Чтение сцены дополнительно вызывает объектную проверку. Чистая функция удара не знает о пользователе и токене.

## Зафиксируйте матрицу ответов

| Условие | Статус | Наблюдаемая граница |
|---|---:|---|
| Заголовок отсутствует | `401` | Пользователь не установлен. |
| Bearer пустой, повреждённый или неизвестный | `401` | Учётные данные не приняты. |
| Токен Ирины, сценарий Антона | `403` | Объектное разрешение отклонило владельца. |
| Токен Антона, сцена отсутствует | `404` | Доступный идентификатор не найден. |
| Токен Антона, его сцена существует | `200` | Аутентификация и разрешение пройдены. |

Ответ 403 не содержит полей чужой сцены.

## Начните с красного теста настоящего заголовка

В `game/tests/test_security.py` создайте пользователей, реальные токены тестовой базы и запросы с `HTTP_AUTHORIZATION="Bearer OPAQUE_TOKEN"`. Первый тест до подключения аутентификации должен показать неверный успешный доступ, затем стать зелёным после реализации.

```bash
python manage.py test game.tests.test_security -v 2
```

Проверьте отсутствие заголовка, пустой Bearer, повреждённый и неизвестный токен, чужую сцену, неизвестную сцену владельца и успех владельца. Прямое присваивание `request.user` не доказывает границу заголовка.

## Защитите четыре операции

Тесты с реальным заголовком должны пройти для:

- инициализации персонажа;
- получения сцены;
- броска кубика;
- расчёта одного удара.

Назначение владельца выполняется сервером. Партию и результат удара сервер по-прежнему не сохраняет.

## Выполните самостоятельный перенос правила

После зелёного маршрута основного сценария без готового фрагмента решения создайте в тестовой базе второй самостоятельный ресурс сценария с другим владельцем и хотя бы одной собственной сценой. Докажите реальными Bearer-заголовками симметричную матрицу: каждый владелец получает `200` для своей сцены и `403` для сцены другого владельца, а отсутствующий идентификатор даёт `404`. Эта проверка должна использовать те же производственные URLconf, представление и класс объектного разрешения, а не подменять `request.user` и не создавать отдельный тестовый маршрут.

В кратком комментарии к тесту укажите, какое общее правило вы перенесли с первого ресурса на второй. Не копируйте реализацию разрешения внутрь теста: новый ресурс должен пройти через общий механизм продукта.

## Обновите OpenAPI

В `components.securitySchemes` объявите HTTP Bearer-схему с непрозрачным токеном. Добавьте требование безопасности четырём операциям и задокументируйте 401, необходимые 403 и 404.

```bash
python manage.py spectacular --file generated-openapi.yaml --validate
python manage.py test game.tests.test_api game.tests.test_security -v 2
```

Swagger UI используется только с временным локальным токеном. После проверки очистите поле авторизации в браузере.

## Проверьте секреты и логи

Токен не должен появиться:

- в Git и `.env.example`;
- в YAML сценария или сохранения партии;
- в URL;
- в прикладном логе;
- в JSON-отчёте проверки.

Логируетcя метод, путь, статус, идентификатор запроса и безопасный код причины. Заголовок `Authorization` маскируется целиком. Реальная передача токена требует HTTPS; локальный HTTP курса не является промышленным развёртыванием.
