# Домашняя работа 4 — SQLite, полный OpenAPI и готовый `console-quest`

## Результат

Завершите первый продукт без Django: перенесите серверный сценарий из YAML в SQLite через идемпотентный импорт, доведите OpenAPI 3.1 до полного контракта четырёх операций, расширьте ациклический граф минимум до восьми достижимых сцен, трёх финалов и одного боя и пройдите A01.

На работу и первую итоговую проверку отводится до 240 минут активного времени, включая 15 минут обязательного чтения, назначенного в L04. Порог A01 — 75%; обязательные предметные границы нельзя компенсировать оформлением.

## Исходное состояние

Начинайте от чистого тега `hw03-ready`:

```bash
git switch main

python -m unittest discover -s client/tests -v

python -m ruff check client server
```

Зафиксируйте зелёный микродедлайн до изменения хранилища. При регрессии сначала восстановите HW03.

## Создайте точное дерево этапа

Создайте:

```text
server/repository.py
server/import_scenario.py
server/tests/test_repository.py
server/tests/test_import_scenario.py
```

Измените только существующие `server/http_server.py`, `server/data/scenario.yaml`, `contracts/openapi.yaml`, `README.md` и при необходимости контейнерную команду сервера. `server/data/game.sqlite3` создаётся во время выполнения и не входит в Git.

## Сначала завершите OpenAPI

До изменения обработчиков опишите в `contracts/openapi.yaml`:

- четыре метода и пути HW03;
- параметры `scene_id`;
- тела и ответы инициализации и удара;
- успешные статусы `200`;
- ошибки `400`, `404` и `405` со стабильным `error.code`;
- переиспользуемые схемы в `components`.

Для удара обязательны состояния `player` и `opponent`, а также `player_roll` и `opponent_roll`. Сервер выбирает атакующего по D17 и не хранит партию. Проверка OpenAPI должна завершиться кодом `0` до согласования реализации.

## Расширьте авторский сценарий

В `server/data/scenario.yaml` самостоятельно создайте не менее восьми сцен, достижимых от стартовой:

- минимум три финала, включая позитивный и негативный;
- минимум одну боевую сцену;
- от двух до четырёх вариантов у сцены выбора;
- существующие цели всех переходов;
- отсутствие циклов и недостижимых сцен.

Литературное качество не оценивается. YAML остаётся версионируемым источником повторного импорта, но рабочий API после импорта не читает его.

## Спроектируйте SQLite-схему

В `server/repository.py` самостоятельно создайте таблицы сценария, сцен, вариантов и боевого действия. Используйте:

- первичные ключи для устойчивой идентичности;
- внешние ключи для связей;
- `NOT NULL` для обязательных полей;
- `UNIQUE` для идентификатора сцены внутри сценария и позиции варианта;
- проверяемые ограничения допустимых видов и чисел.

Включите `PRAGMA foreign_keys = ON` для каждого соединения. Все значения запроса передавайте параметрами, не склеивайте SQL со строкой пользователя.

## Начните с красного теста репозитория

В `server/tests/test_repository.py` создайте тест временной базы: схема создаётся, сцена записывается и читается по идентификатору. До реализации получите ожидаемый `NotImplementedError`, затем зелёный результат:

```bash
python -m unittest server.tests.test_repository -v
```

Добавьте тесты внешнего ключа, уникальности и простого `JOIN`, связывающего сценарий со сценами.

## Реализуйте идемпотентный импорт

`server/import_scenario.py` принимает путь YAML и путь SQLite, полностью проверяет граф до изменения базы и выполняет запись в транзакции.

Повторный запуск с теми же данными оставляет тот же набор строк. Ошибка в середине откатывает весь импорт. Удаление отсутствующих в новой версии сцен выполняется только внутри транзакции и не затрагивает другие сценарии.

Наблюдаемая команда:

```bash
python -m server.import_scenario --source server/data/scenario.yaml --database server/data/game.sqlite3
```

Первый и второй запуски завершаются кодом `0`, а количества строк совпадают.

## Переключите сервер на репозиторий

После успешного импорта `server/http_server.py` получает сцену только через `repository.py`. Переименуйте YAML и запустите HTTP-тесты: ответы должны сохраниться. Верните исходное имя после наблюдения.

Инициализация читает стартовую сцену и характеристики из SQLite. Бросок и чистый расчёт удара сохраняют контракт HW03.

## Проверьте граф внешним средством

Внешняя проверка должна подтвердить минимум восемь достижимых сцен, три финала, один бой, отсутствие циклов и неизвестных ссылок. Не добавляйте алгоритм проверки в продукт только ради проверки: граф проверяет средство курса.

## Проверьте Compose и том

```bash
docker compose build
docker compose run --rm server python -m server.import_scenario --source server/data/scenario.yaml --database /data/game.sqlite3
docker compose up -d server
docker compose run --rm client
docker compose down
docker compose up -d server
docker compose logs server
docker compose down
```

Обычный `down` сохраняет `server-data`; `down -v` в приёмочном маршруте не используйте. После повторного запуска сервер читает базу из тома.

## Проверьте Swagger UI

Откройте локальную страницу Swagger UI из утверждённой конфигурации курса и выполните `GET` существующей сцены. Отдельно сохраните:

- код `0` валидатора OpenAPI;
- успешный фактический GET;
- зелёные контрактные тесты.

Эти три свидетельства проверяют разные границы и не заменяют друг друга.
