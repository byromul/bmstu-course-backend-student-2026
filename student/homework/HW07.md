# Домашняя работа 7 — четыре операции DRF и OpenAPI

## Результат

Продолжите `django-quest`: реализуйте через Django REST Framework четыре игровые операции, перенесите утверждённый OpenAPI 3.1-контракт, подключите локальный Swagger UI и подтвердите позитивные и негативные ответы тестами. Защита Bearer появится только в HW08.

На работу отводится до 150 минут активного времени, включая 15 минут обязательного чтения, назначенного в L07.

## Исходное состояние

Начинайте от чистого тега `hw06-ready`:

```bash
git switch main

python manage.py makemigrations --check --dry-run
```

Импортированный сценарий должен быть доступен в новой локальной базе.

## Перенесите только контракт

Создайте каталог `contracts` и скопируйте принятый `contracts/openapi.yaml` из `console-quest` в `django-quest/contracts/openapi.yaml` отдельной наблюдаемой операцией.

Не копируйте HTTP-сервер, SQLite-файл или клиент первого продукта. Контракт является известной границей; DRF-реализация создаётся заново.

## Создайте точное дерево этапа

Создайте:

```text

game/serializers.py
game/combat.py
game/api_views.py
game/api_urls.py
game/tests/test_api.py
game/tests/test_combat.py
```

Измените `quest/settings.py` и `quest/urls.py` для подключения `rest_framework`, `drf_spectacular`, схемы и документации.

## Зафиксируйте четыре операции

Реализуйте:

| Метод и путь | Успех | Источник результата |
|---|---:|---|
| `POST /api/v1/characters/initialize` | `200` | Стартовая сцена и характеристики сценария из ORM. |
| `GET /api/v1/scenes/{scene_id}` | `200` | Сцена, варианты или боевое действие из ORM. |
| `POST /api/v1/dice/rolls` | `200` | Целое `value` от 1 до 6. |
| `POST /api/v1/combat/attacks/resolve` | `200` | Чистый расчёт одного удара по телу запроса. |

Неизвестная сцена даёт `404`, неверное тело — `400`, известный путь с неверным методом — `405`. Защита и статусы 401/403 пока отсутствуют.

## Реализуйте сериализаторы

Сериализаторы должны:

- проверять вложенные состояния участников;
- требовать целые броски от 1 до 6;
- выдавать внешние ключи `str` и `def` независимо от имён Python-полей;
- формировать единый ответ сцены;
- не принимать серверные поля модели, которых нет в контракте.

Представление использует только `validated_data` после успешной проверки.

## Реализуйте чистую функцию удара

В `game/combat.py` создайте функцию, не зависящую от Django, DRF, ORM и запроса. Она получает атакующего, защитника и два броска, возвращает `damage`, новое состояние защитника и `outcome`, не изменяя аргументы.

Сначала получите красный тест, затем зелёный:

```bash
python manage.py test game.tests.test_combat -v 2
```

Проверьте обычный удар, равные броски, защиту выше атаки, нулевой HP и неизменность исходного словаря.

## Реализуйте представления и маршруты

`game/api_views.py` координирует сериализатор, ORM или чистую функцию и возвращает `Response` с явным статусом. `game/api_urls.py` объявляет четыре пути.

Предметное правило боя не размещайте внутри представления. Операция удара не сохраняет партию или результат в базе.

## Стабилизируйте ошибку

Контролируемые ошибки имеют форму:

```json
{
  "error": {
    "code": "method_not_allowed",
    "message": "Метод не поддерживается"
  }
}
```

Тесты проверяют статус и `error.code`, а не полный русский текст. `GET /api/v1/dice/rolls` обязан вернуть `405` и `error.code = "method_not_allowed"`.

## Подключите drf-spectacular

Добавьте приложения и настройки схемы механической конфигурацией, затем маршруты:

- `/api/schema/` для OpenAPI;
- `/api/docs/` для Swagger UI.

Сопоставьте с перенесённым договором все четыре операции, параметры, тела, ответы и ошибки.

## Добавьте контрактные тесты

В `game/tests/test_api.py` проверьте:

- четыре успешных запроса;
- реальный диапазон броска;
- `400` для неверных бросков и неполного состояния;
- `404` для неизвестной сцены;
- `405` для запрещённого метода;
- JSON `Content-Type` и стабильный `error.code`;
- отсутствие изменения моделей после операции удара.

Тесты используют DRF APIClient и фактическую тестовую базу.
