# Конспект лекции 5 — новый проект Django

Материал дополняет слайды L05. HW05 начинает `django-quest` в отдельном пустом каталоге и не продолжает дерево первого продукта.

## Фреймворк и инверсия управления

Фреймворк предоставляет компоненты и управляет общим жизненным циклом. При обычном вызове приложение выбирает библиотечную функцию; в Django фреймворк принимает запрос, по URLconf выбирает представление и вызывает прикладной код.

Соглашения уменьшают ручную связку, но требуют понимать структуру и предусмотренные точки расширения.

## Проект и приложение

Команды создания:

```bash
python -m django startproject quest .
python manage.py startapp game
```

`manage.py` выбирает настройки. Пакет `quest` содержит конфигурацию проекта, корневой URLconf и точки ASGI/WSGI. Приложение `game` содержит предметные представления, модели, тесты, шаблоны и миграции.

`INSTALLED_APPS` подключает приложение к общему жизненному циклу.

## Путь запроса

Типовой путь:

1. Django получает HTTP-запрос;
2. корневой URLconf включает маршруты приложения;
3. URLconf выбирает представление;
4. представление создаёт ответ;
5. промежуточное ПО обрабатывает запрос или ответ на общей границе.

`python manage.py check` проверяет конфигурацию; тестовый клиент проверяет поведение маршрута.

## Наследование

Производный класс является частным видом базового и получает его интерфейс. Django ожидает конкретные методы и точки переопределения. Изменение одного метода не должно ломать ожидаемую сигнатуру.

## SSR и шаблоны

SSR объединяет шаблон и контекст на сервере и возвращает готовый HTML. Именованный маршрут строится через `reverse`, базовый шаблон задаёт общую структуру, дочерний — содержимое, статические файлы подключаются через `static`.

Автоматическое экранирование защищает HTML-границу. Изменяющие HTML-формы требуют CSRF-защиту.

JSON API — отдельная граница: он возвращает `application/json`, а не готовую HTML-страницу.

## Автономная капсула

```bash
python student/lectures/capsules/L05/check_all.py
```

Капсула создаёт минимальные настройки в памяти и проверяет `GET /health/` через URLconf и представление. Она не читает `django-quest`.

## Самопроверка

Приложение само вызывает библиотечную функцию. Django по URLconf выбирает и вызывает представление. Это наблюдаемое различие направления вызова.
